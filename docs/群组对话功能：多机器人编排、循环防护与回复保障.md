# 群组对话功能：多机器人编排、循环防护与回复保障

**作者：Manus AI**  
**日期：2026-08-12**  
**适用范围：** 一个或多个真人用户与多个预设角色机器人共用同一对话线程的产品。本文聚焦服务端逻辑、可靠性和可审计性，而非模型提示词文案或前端视觉设计。

## 执行结论

这个需求的难点不在于“让多个机器人都能调用模型”，而在于把每条人类消息转换为一项**可持久化、可追踪、最终必须结案的回复义务**（`reply_obligation`）。推荐默认采用“**人类事件触发，协调器一次性规划，机器人受限执行，至少一个可见结果结案**”的结构：机器人发言不会再次触发机器人调度；多机器人讨论只在显式、有限、可验收的工作流中发生。

当前主流框架的共同方向是以协调器或状态图控制代理，而不是把代理输出直接串成开放式自回路。AutoGen 提供自定义发言者选择和显式终止；Semantic Kernel 在每轮中先检查人工输入与终止条件，再选择下一个代理；LangGraph 以递归步数限制兜底；OpenAI Agents SDK 则用单次运行的最大轮次约束交接循环。[1] [2] [3] [4] [5] 因此，建议把“自由群聊”降级为少数场景下的受控模式，而把默认体验设计成**一次人类输入对应 1 个主答复，加 0–1 个有价值的补充答复**。

> **核心不变量：** 只有来自人类用户的、已提交的消息可以创建 `reply_obligation`；任何机器人消息都不能创建新的 `reply_obligation`。每项义务要么由至少一条可见机器人消息满足，要么在极端故障下由明确的降级/升级消息满足。

下图展示推荐的可靠链路。其要点是：在人类消息入库的同一事务中写入回复义务和 Outbox 事件，之后再异步调度机器人。这样避免“消息保存成功、机器人任务却丢失”的双写问题；事务性 Outbox 是业内用于可靠事件投递的成熟模式。[6]

## 一、行业方案的共同规律与取舍

### 1.1 从框架能力看，控制权必须留在协调层

| 方案或资料 | 已公开的控制机制 | 对本需求的直接启示 | 不宜直接照搬之处 |
|---|---|---|---|
| AutoGen GroupChat | 自定义发言者选择函数可依据历史与成员选择指定代理、内置策略或返回 `None` 结束；示例采用状态流并配置最大轮数。[2] | 用允许迁移图与状态机表达“谁能说话、何时结束”。 | 产品默认群聊不应使用随机或无约束自动轮询。 |
| Semantic Kernel Group Chat | Manager 每轮按“是否请求用户输入 → 是否终止 → 结果处理 → 选择下一代理”的顺序运行，并支持最大调用数。[3] | 先判终止、再调度；人工输入是暂停/恢复边界。 | 不要让各机器人自行决定是否继续下一轮。 |
| LangGraph | `StateGraph` 在触达停止条件前超过递归限制时终止，并将循环边视为常见原因。[4] | 需要图级或会话级步数预算作为最后熔断器。 | 步数上限是安全网，不能取代业务完成条件。 |
| OpenAI Agents SDK | 运行器处理工具调用与交接；`max_turns` 超限会产生明确异常，运行器提供错误处理扩展点。[5] | 每次人类发言应拥有独立的轮次、时间和成本预算。 | 代理间 handoff 仍可能来回转移，不能把“交接”当作天然安全。 |
| Azure 架构中心 | 把群聊、并发、顺序、handoff 区分为不同模式；明确提醒群聊越多代理越难控制，建议限制到三个或更少。maker-checker 循环应具备验收标准、迭代上限和回退动作。[1] | 选择模式应先于选择模型；多视角回答优先使用扇出—汇聚，而不是让机器人互聊。 | 开放式“圆桌辩论”不适合作为普通客服/问答的默认路径。 |

因此，系统不能仅配置“角色 Prompt + 群聊历史”。它还需要一个**确定性协调器**：其输入是事件、成员能力、当前工作流状态、预算和策略；其输出是一个有限的回应计划（`response_plan`）。模型可以帮助分类或排序，但不能拥有创建无限后续回合的权限。

### 1.2 四种交互模式应分开实现

| 模式 | 适用情形 | 调度方式 | 默认上限 | 用户可见结果 |
|---|---|---|---|---|
| **A. 单主答复** | 客服、常规问答、知识咨询 | 规则/轻量分类器选 1 个主机器人 | 1 次机器人执行 | 1 条主答复；这是默认模式。 |
| **B. 主答复 + 补充** | 用户显式点名多个角色，或问题同时跨两个稳定领域 | 选 1 个主机器人与最多 1 个补充机器人；可并发 | 2 条可见机器人消息 | 主答复先结案，补充在时限内到达则追加。 |
| **C. 扇出—汇聚** | 需要多视角比较、投票、交叉验证 | 多机器人对同一人类消息独立产出内部意见，再由协调器/总结者汇聚 | 2–3 个专家 + 1 次汇聚 | 建议只展示总结者；专家意见可按需展开。 |
| **D. 受控 maker-checker** | 草稿—审校、代码评审、合规校验等确有迭代价值的任务 | 固定 `maker → checker → maker` 状态机 | 1–2 次返工、明确验收条件 | 最终由固定“对外发言人”发布；未通过则说明限制或转人工。 |

模式 A/B 足以覆盖绝大多数产品需求。模式 C 实际上比开放式群聊更适合“多个机器人都给意见”的体验，因为各机器人互不触发、可并发执行，最后由一个稳定角色处理冲突。模式 D 是唯一允许机器人间产生工作依赖的模式，但它必须是预定义状态图，不能是“任一机器人看到任一消息都可继续说话”。这与 Azure 对群聊、并发与评审循环的区分一致。[1]

## 二、推荐的逻辑架构

### 2.1 以“回复义务”而不是“机器人任务”定义成功

对于每条已提交的人类消息 `H`，在同一数据库事务内创建：人类消息记录 `M(H)`、唯一的回复义务 `O(H)`，以及一条待投递的 `HumanMessageAccepted` Outbox 事件。`O(H)` 的唯一键为 `(group_id, human_message_id)`，因此重复点击发送、网络重试或消息队列至少一次投递都不会制造第二项义务。

协调器领取该事件后，产生 `response_plan`。计划有且仅有一个 `primary_bot_id`，并可包含有限数量的 `secondary_bot_ids`；计划也带有 `deadline`、`bot_turn_budget`、`cost_budget`、`workflow_mode` 与 `causation_id`。只要主机器人或降级机器人成功提交一条可见消息，`O(H)` 即置为 `FULFILLED`。补充机器人失败不影响已满足的主回复义务。

这一区分非常关键。若把“每一个机器人任务都成功”作为定义，系统会为了等待慢机器人而延迟用户体验；若只把“队列里有任务”作为定义，则故障时会默默失约。回复义务提供了面向用户的完成语义，任务只是实现它的可替换手段。

### 2.2 关键实体和不可变约束

| 实体 | 关键字段 | 作用与约束 |
|---|---|---|
| `groups` | `id`、`owner_id`、`mode`、`status` | 创建者为人类成员；`status=ACTIVE` 时才可接收新消息。 |
| `members` | `group_id`、`member_type`、`role_key`、`enabled` | `member_type ∈ {HUMAN, BOT}`；创建群组时校验至少 1 人类和 1 启用机器人。 |
| `bot_profiles` | `role_key`、`domains`、`persona`、`priority`、`fallback_rank` | 配置“客服、技术、幽默”等角色、可处理意图、风险级别与兜底顺序。人格只影响语气，不能覆盖安全、权限或路由规则。 |
| `messages` | `id`、`sender_type`、`content`、`causation_id`、`idempotency_key` | 机器人消息必须携带它所响应的人类消息 `causation_id`；数据库唯一键阻止重复提交。 |
| `reply_obligations` | `human_message_id`、`state`、`deadline_at`、`primary_bot_id`、`fulfillment_message_id` | **一条人类消息一条义务**；仅 `FULFILLED` 或明确 `DEGRADED_FULFILLED` 才是用户可接受结案。 |
| `response_plans` | `obligation_id`、`mode`、`turn_budget`、`deadline_at`、`plan_version` | 协调器的不可变决策快照，便于复盘与防止并发改写。 |
| `agent_runs` | `plan_id`、`bot_id`、`attempt`、`status`、`input_hash` | 单个机器人执行记录；同一 `(plan_id, bot_id, attempt)` 只可开始一次。 |
| `outbox_events` | `event_id`、`aggregate_id`、`type`、`processed_at` | 和消息、义务一起落库，再由中继可靠发布。 |

数据库层应额外验证以下约束：其一，任何 `sender_type=BOT` 的消息不能创建 `reply_obligation`；其二，`FULFILLED` 必须引用一条存在且可见的机器人消息；其三，计划中的机器人必须是该群当前启用成员；其四，同一义务的完成状态必须采用比较并交换（CAS）或条件更新，防止两个并发 worker 同时把不同结果写成“首个答复”。

### 2.3 角色建模与确定性路由

角色配置可以简单，但调度规则应可解释。建议给每个预设机器人维护 `domains`、`keywords`、`explicit_mentions`、`priority`、`availability` 与 `cooldown`。例如，客服机器人负责订单/账户/售后，技术机器人负责 API/报错/配置，幽默机器人只在非严肃情形为主答复增加轻量表达，而不承担支付争议、医疗、法律等高风险问题。

候选排序可以采用规则优先、模型辅助的混合式方法：

\[
score(b,m)=4\cdot mention+3\cdot domain+2\cdot keyword+priority-3\cdot risk-2\cdot unavailable-2\cdot repetition
\]

其中 `mention` 表示用户明确 @ 某角色；`domain` 是由规则或轻量意图分类获得的领域匹配；`repetition` 防止同一机器人在没有新增价值时重复参与。该公式的重点不是固定权重，而是让路由可测试、可调试、可降级。若 LLM 路由器不可用、输出不合法，系统仍能以关键词、点名和静态优先级选出主机器人；若无任何候选，则选择 `coordinator_bot`，而不能返回“无人可答”。

> **路由必须是可失败的增强能力，不得是回复保证的单点依赖。** 模型可以建议“技术机器人更合适”，但在其失败时，协调器要能立即用静态规则指定默认协调机器人。

## 三、三项核心挑战的完整解决方案

### 3.1 挑战一：多机器人响应规则

建议采用“**一主、多补、先主后补**”策略。协调器先找出唯一主机器人；主机器人产生成功的可见答复后，回复义务立即结案。只有在满足下列任一条件时，才启动不超过一个补充机器人：用户显式点名多个角色；路由判断为两个独立领域且补充内容互补；或群组开启了“多视角”模式。补充任务应携带“不得重复主答复、只补充 X 维度”的结构化指令，并具有短于主答复的截止时间。

当问题需要真正的多方判断时，应该在后台采用扇出—汇聚而非可见聊天接龙。例如，技术机器人、客服机器人各生成内部 `advice`，由协调机器人检查冲突并输出一条合成答案。该模式既能保留多专业视角，又避免用户看到三段重复内容和机器人间无目的互评。并发模式的独立执行与汇总策略也符合公开架构指引。[1]

| 路由输入 | 推荐决策 | 可见发言者 | 保障逻辑 |
|---|---|---|---|
| “@技术机器人，为什么 API 报 401？” | 技术机器人为主 | 技术机器人 | 技术角色不可用时，协调机器人按技术故障模板回应并说明正在升级。 |
| “我的订单退款在哪里？” | 客服机器人为主 | 客服机器人 | 无法查到订单时，仍给出下一步所需信息或人工转接说明。 |
| “从技术、客服两个角度比较这个方案” | 扇出—汇聚 | 协调机器人，可选显示两个署名摘要 | 主汇聚者是唯一结案人；专家超时不会阻塞保底答复。 |
| “请写文案并检查合规” | maker-checker | 文案机器人或协调机器人最终发布 | 返工次数到顶时返回当前版本与未解决风险。 |
| 闲聊或意图不明 | 协调机器人为主，可带幽默风格 | 协调机器人 | 通过澄清问题满足本轮回复义务。 |

### 3.2 挑战二：防止机器人循环对话

循环防护必须分层；只设置“最多 10 轮”不够，因为即便 10 轮也会制造成本、延迟和不可信体验。推荐的六层机制如下。

| 层级 | 机制 | 阻断的故障 | 必须性 |
|---|---|---|---|
| 事件源头 | 仅 `HUMAN_MESSAGE_CREATED` 创建回复义务；`BOT_MESSAGE_CREATED` 只做展示和审计。 | 最常见的“机器人看到机器人继续回答”。 | **必需** |
| 拓扑约束 | 维护允许迁移图；默认无 `BOT → BOT` 边，maker-checker 仅允许固定边。 | 任意角色之间的意外反复交接。 | **必需** |
| 状态机 | 每条边要求前置条件，例如 checker 只有在收到 maker 产物且未超预算时才能发言。 | 状态无变化的空转。 | **必需** |
| 预算熔断 | `bot_turn_budget`、最大 handoff、每义务时限、模型调用成本、每角色连续发言上限。 | 配置错误、模型异常或逻辑漏网。 | **必需** |
| 进展判定 | 连续两次产物哈希相近、无新证据、相同角色重复、任务账本无状态变化时停止。 | “换句话说”式低价值反复。 | 强烈建议 |
| 人工边界 | 高风险、置信度低、验收不通过或预算耗尽后升级；不把升级消息当成再次调度信号。 | 无法自动收敛的问题。 | 强烈建议 |

“机器人不能触发机器人”是面向普通群聊的最强、最简单规则；它允许每轮人类消息触发多个机器人，但调度权始终属于服务端协调器。若业务确实需要机器人协作，则每一步都必须带 `causation_id`、`workflow_id`、`step_no`、`remaining_turns` 和明确的停止条件。AutoGen 的状态流、Semantic Kernel 的 manager 生命周期、LangGraph 的递归限制均支持这一“显式控制流优先”的思想。[2] [3] [4]

### 3.3 挑战三：确保人类消息至少获得一个机器人回复

严格来说，任何分布式系统在数据库、队列、模型服务和网络同时不可用时，都无法物理保证“任意时间内一定生成高质量 LLM 内容”。因此必须把产品承诺拆成两层：第一层是**持久化承诺**，即已接受的人类消息不会丢失其回复义务；第二层是**可见性承诺**，在目标服务等级时间内，系统成功写入一条正常机器人答复或明确的降级机器人答复。

具体实现是使用 Outbox、至少一次投递与幂等提交。事务提交时把人类消息、`PENDING` 义务和 Outbox 事件原子写入；后台中继反复投递未处理事件；worker 以义务 ID 领取任务；消息写入通过唯一幂等键去重；超时扫描器重新投递长期 `PENDING/RUNNING` 义务。事务性 Outbox 通过同事务保存业务数据和待发事件避免事件丢失，而消费者仍必须能容忍重复投递。[6]

降级顺序应预先确定，不能在故障时再调用复杂模型作决定。推荐顺序为：目标角色重试一次 → 可处理该领域的替代机器人 → 默认协调机器人 → 无模型依赖的静态系统答复（仍以“协调机器人”身份显示）→ 人工队列/工单。静态答复不应假装已解决问题，例如：“我暂时无法完成专业核验，已记录你的问题；请补充订单号/错误时间，或稍后重试。”它满足“不会沉默”的体验底线，并保护事实正确性。

## 四、关键流程伪代码

下面的伪代码刻意把持久化、路由和模型执行分离。它不是特定语言实现，但可映射到 Java/Spring、Node/NestJS、Python/FastAPI 等服务端。

```python
async def accept_human_message(cmd: SendMessage) -> str:
    assert cmd.sender_type == "HUMAN"
    validate_group_is_active(cmd.group_id)

    async with db.transaction():
        message = insert_message_if_absent(
            group_id=cmd.group_id,
            sender_id=cmd.sender_id,
            sender_type="HUMAN",
            content=cmd.content,
            idempotency_key=cmd.client_message_id,
        )

        obligation = upsert_reply_obligation(
            group_id=cmd.group_id,
            human_message_id=message.id,
            state="PENDING",
            deadline_at=now() + seconds(15),
        )

        insert_outbox_once(
            event_type="HumanMessageAccepted",
            aggregate_id=obligation.id,
            dedupe_key=f"reply-obligation:{obligation.id}",
        )

    return message.id


async def process_reply_obligation(obligation_id: str):
    obligation = claim_if_not_final(obligation_id)
    if obligation is None:
        return  # 已完成、被其他 worker 领取，或重复消息

    plan = load_or_create_plan(obligation, router=hybrid_router)
    # hybrid_router 永远返回一个 primary；无匹配时为 coordinator_bot。

    primary_result = await run_bot_with_budget(
        bot_id=plan.primary_bot_id,
        human_message_id=obligation.human_message_id,
        turn_budget=plan.turn_budget,
        deadline_at=plan.deadline_at,
    )

    if is_publishable(primary_result):
        first_message = commit_visible_bot_message_once(
            obligation_id=obligation.id,
            sender_bot_id=plan.primary_bot_id,
            content=primary_result.content,
            causation_id=obligation.human_message_id,
        )
    else:
        fallback = await run_fallback_chain(plan, obligation)
        first_message = commit_visible_bot_message_once(
            obligation_id=obligation.id,
            sender_bot_id=fallback.bot_id,
            content=fallback.safe_content,
            causation_id=obligation.human_message_id,
        )

    mark_fulfilled_cas(obligation.id, fulfillment_message_id=first_message.id)
    # 之后的 secondary 是“可选补充”，绝不创建新 obligation。
    enqueue_optional_secondary_runs_if_still_useful(plan, obligation)


async def on_bot_message_created(message):
    persist_for_history_and_audit(message)
    publish_to_realtime_clients(message)
    return  # 故意不产生 HumanMessageAccepted，也不触发机器人调度
```

`commit_visible_bot_message_once` 应同时做到两件事：写入机器人消息，并通过 `UPDATE ... WHERE state NOT IN ('FULFILLED', 'DEGRADED_FULFILLED')` 或行锁竞争完成义务。即便多个 worker 在网络抖动后都认为自己需要兜底，也只有首个事务可完成义务；后到事务读取到已完成状态后退出或把结果转为不展示的审计记录。

## 五、异常、超时与安全回退矩阵

| 事件 | 协调器动作 | 是否重试 | 对用户的最小可见结果 | 绝不能做的事 |
|---|---|---|---|---|
| 没有角色命中 | 选 `coordinator_bot`，提出澄清或给通用答复。 | 否 | 一条协调机器人答复。 | 因路由置信度低而沉默。 |
| 目标机器人模型超时 | 有界指数退避后切换候补角色。 | 1 次或在剩余时限内 | 候补答复；必要时说明延迟。 | 无限制重试同一模型。 |
| 所有模型不可用 | 直接使用静态降级文案并创建人工/延迟处理记录。 | 后台可恢复性重试 | 明确“暂不可用”的机器人消息。 | 伪造已查询或已解决。 |
| 队列或 worker 停机 | Outbox/超时扫描器重新投递；按 `obligation_id` 幂等领取。 | 是 | 恢复后补发；若超出 SLA，先发降级答复。 | 仅把任务留在内存。 |
| 重复事件或用户重复提交 | 用客户端 idempotency key 与义务唯一键去重。 | 不适用 | 一条正常答复。 | 向用户展示两三条相同机器人消息。 |
| 机器人互相点名或要求继续 | 拒绝由机器人消息创建的调度事件。 | 否 | 当前轮结案或按已批准计划继续。 | 信任模型文本中的“请让 X 继续回复”。 |
| maker-checker 未通过且预算耗尽 | 输出当前最佳版本、未通过项与升级路径。 | 否 | 清晰质量告警。 | 无穷返工，或把未通过产物伪装成通过。 |
| 并发抢占同一义务 | 使用行锁/CAS，败者丢弃或转审计。 | 不适用 | 只展示首个满足者。 | 让多个结果都标记为“首个官方答复”。 |

## 六、可观测性、测试与验收标准

没有观测就无法证明“保证回复”。建议对每项回复义务产生 trace，并将人类消息、计划、每次代理调用、最终可见消息和回退原因关联到同一个 `correlation_id`。应把原始提示词与敏感业务数据做最小化或脱敏存储，而不是把全量用户内容无限期写进日志。

| 指标 | 定义 | 建议目标或告警 |
|---|---|---|
| `reply_obligation_fulfillment_rate` | 在 SLA 内进入 `FULFILLED/DEGRADED_FULFILLED` 的义务比例 | 目标不低于 99.9%；跌破阈值立即告警。 |
| `time_to_first_bot_reply` | 人类消息提交到首条可见机器人消息的耗时 | 观察 p50/p95/p99，并按群组模式分别统计。 |
| `fallback_rate` | 使用候补或静态答复的比例 | 突增通常意味着模型、路由或下游依赖故障。 |
| `bot_turns_per_obligation` | 每条义务实际执行的机器人轮数 | 超出模式预算即为缺陷或疑似循环。 |
| `rejected_bot_trigger_count` | 机器人消息试图触发调度而被拒绝的次数 | 非零可接受，但异常激增说明提示词/接口被误用。 |
| `outbox_lag` | 最早未处理 Outbox 事件的年龄 | 超过回复 SLA 的一半即升级告警。 |
| `duplicate_suppressed_count` | 被幂等键拦截的重复提交/重复消费量 | 用于发现客户端或队列重投递问题。 |

测试不应只覆盖“LLM 正常回复”。至少应进行以下验收：对同一 `client_message_id` 并发提交 100 次，验证只存在一条义务和一条主可见答复；人为让主机器人超时，验证候补或静态答复在截止时间前写入；人为重复投递 Outbox，验证不会重复展示；在 maker-checker 中让 checker 永不通过，验证恰好在迭代上限结束；让机器人文本包含“请技术机器人继续”，验证不会创建新义务；停掉队列消费者后恢复，验证所有未完成义务最终被扫描并结案。

## 七、实施优先级与现实边界

第一版不必实现复杂的自由多智能体协商。建议先交付：群组/成员/角色配置；`reply_obligation + outbox + 幂等`；混合路由与协调机器人兜底；默认单主答复；机器人消息不触发调度；基础 trace 和告警。第二版再增加主答复加补充、扇出—汇聚和明确的 maker-checker 工作流；在真实数据证明存在需求前，不要开放任意机器人互相交谈。

最后，需在产品文案中准确表述“保证回复”。工程上可承诺的是：**一旦服务端确认接收人类消息，系统会持久化其回复义务，并在正常依赖可用时生成主答复；依赖失败时，系统用降级机器人或升级通知避免无声失败。** 这比声称“每个机器人永远都会回复”更诚实、更可度量，也更符合分布式系统现实。
